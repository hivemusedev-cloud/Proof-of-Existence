# poe-node

The Proof of Existence blockchain node, built in Rust against the verified
Lean specification (`Proof_of_Existence_v1_1_1_CC.lean`).

## Increment 1 — poe-kernel (this build)

A definition-for-definition port of the Lean kernel's core:

- `crates/poe-kernel/src/lib.rs` — claims (`Spend`), settlement (`settle`,
  `register`, `first_tx`, `evidence`), multi-height settlement (`settleM`),
  the money constants and grant law (`pot`, `grant`, `emission`), and a
  stateful `Registry` over the kernel's ten registry kinds.
- `crates/poe-kernel/src/ledger.rs` — notes, assets, the five acts
  (`Op::Join / Create / Issue / Transfer / Tick`), validity predicates, and
  the genesis ledger, mirroring the Lean `Ledger`/`act`/`runOps`.
- `crates/poe-kernel/tests/kernel_batteries.rs` — acceptance batteries
  modelled on the Fortran twin's T1/T2 streams and on the Lean theorems
  (`settle_nodup`, `settle_canonical`, `merge_registers_the_union`,
  `evidence_is_complete`, cap and window rules).
- `crates/poe-node` — a small demo binary: genesis → join → close → spend →
  double-spend refused.

Deliberate porting choices: std-only (no dependencies in the kernel); Lean
`Nat` becomes `u64` (heights/ids) and `u128` (value sums); Lean's division
by zero = 0 is preserved in `pot_share`.

## Increment 2 — the renewal act (Step 0, done 2026-11-13)

Approved design: `~/workspace/poe-build-2026-11-11/RENEWAL_ACT_DESIGN_DRAFT_2026-11-11.md`.
The Lean kernel was extended first (`~/workspace/poe-build-2026-11-11/lean-extension/`):
`Op.renew` + `validRenew` + a `claimants` field on `Ledger` (machines that have
claimed in the open epoch, cleared at the close — one claim per machine per
epoch, kernel-enforced). New proofs: `a_close_mints_one_grant_a_claimant`,
`join_then_no_renew`, `renew_then_no_renew`, `renew_then_no_join`,
`a_close_clears_the_claims` — all axiom-free. All three Lean files (kernel,
Liquidity, Tokenomics) recompile on Lean 4.19.0 with zero output, pins silent;
the Tokenomics envelope theorems now cover histories containing renewals,
machine-checking §16.4's "renewal raises no bound". The original verified
copies in `~/workspace/poe-verify-2026-11-10/` are untouched.

Rust port: `Op::Renew` + `valid_renew` + `Ledger.claimants` in poe-kernel;
Tick needed no change — renewal notes ride the same `regs` list and are born
at the close at the epoch's grant. Acceptance battery R1–R6 in
`kernel_batteries.rs` (unregistered/non-fresh refused, join+renew paid alike
at caps MAX/7/0, double claim refused, grant spends exactly once, empty-pot
edge). Suite: 9/9.

## Increment 3 — crypto carriers (Step 2, done 2026-11-13)

`crates/poe-crypto` (10/10 tests):

- `hash` — `H`, byte-for-byte the Compute Seed's construction: SHAKE256
  under `b"PoE/" + tag`, length-framed parts, naturals in 64-byte
  big-endian, 512-bit output. Test vectors generated by the Python original
  match exactly. Merkle commitments ported with the seed's odd-node-carried-up
  rule and empty-root constant.
- `tickets` — hash-chain proposal tickets: commit the tip, reveal one link
  per round, hashing forward verifies; win below `16/A` of the range.
  Boundary test is exact (the reference ticket wins at A=25, loses at 26);
  a 4,000-reveal census at A=200 lands near the expected ~320 winners.
- `xmss` — one-time vote keys: WOTS+ leaves (w=16) under a Merkle tree.
  The state discipline is the deliverable: an index is reserved and the
  state file persisted (write + fsync + atomic rename) *before* any
  signature is produced, so a crash burns a leaf but can never reuse one —
  covered by a crash-simulation test. Single-tree member of the family;
  the manual's 2^40-leaf multi-tree layering + production audit are Step 5
  hardening, stated in the module docs.
- `pq` — ML-DSA-87 (signatures, 4,627-byte sigs) and ML-KEM-1024 (messaging
  key establishment) as thin wrappers over the audited `fips204`/`fips203`
  crates; no cryptography implemented in-house. SLH-DSA not wired — ML-DSA
  covers the signature carrier; SLH-DSA stays a named alternative.

## Increment 4 — storage (Step 3, done 2026-11-13)

`crates/poe-store` (5/5 tests), plus kernel additions `Ledger::pruned`
(the Lean `pruneL`, ported), `Ledger::accepts` / `is_input_ok`, and
`Registry::restore`:

- Canonical encoding (fixed-width big-endian) for notes, acts, ledgers,
  spends — identical bytes on every machine.
- Append-only act log (length-framed, checksum per record) + atomic
  snapshots; replay on open rebuilds the ledger, and a torn tail from a
  crash mid-write is detected and dropped, never applied (tested).
- Per-epoch **state roots**: at each close, `H("state-root", …)` chaining
  the previous root, epoch, minted, live coin, a running births
  accumulator, and set sizes. Pruning never touches the root chain, so
  pruned and full nodes with the same history hold the same roots.
- Pruning verdict battery (T16 mirror at battery scale): a history run
  530 epochs — past the 522 window — then 10 candidate acts (replayed
  join, fresh join, renewals, creates, issues at/over the kept remainder,
  burned and dead inputs) whose verdicts agree between full and pruned,
  plus the input-verdict statement of `the_window_is_enough` itself.
  Scoping, stated in the test: candidates use genuinely fresh marks, as
  honest acts do; reusing a *forgotten* mark is the one case pruning
  cannot see, by design.
- Cuckoo filter over window nullifiers: no false negatives (10,000/10,000
  found), false positives under the 1% bound — an index only; verdicts
  always confirm against the exact death set.
- Backend note: the store is the workspace's own log+snapshot format
  behind the `Store` API. The API is the contract; a RocksDB backend can
  replace the files behind it later without touching callers (its C++
  build is deliberately not pulled into this workspace yet).

## Increment 5 — ordering + finality + networking (Step 4, done 2026-11-13)

Built exactly as BUILD_FLOW Step 4 specifies — three new crates:

- `crates/poe-dag` (3/3 tests) — BlockDAG assembly and **GHOSTDAG
  linearization implemented from the PHANTOM/GHOSTDAG spec**: selected
  parent by blue score, mergeset considered in decreasing blue-score
  order, a candidate is blue iff at most `k` current blues sit in its
  anticone. Content-addressed blocks (`H("block", …)`), so the total
  order is a pure function of the block set — the battery proves two
  DAGs fed the same 60 blocks in different valid orders produce the
  identical linearization and identical blue scores. This replaces the
  manual's imported ordering assumption with tested code.
- `crates/poe-finality` (2/2 tests) — round beacons (`H` over the
  selected tip, domain-separated); proposal draws verified against the
  committed ticket chain under the manual's 16/A rule; committees
  sampled by tickets (target 32); XMSS one-time votes with leaf-reuse
  rejection; **>2/3 finality**; double-proposals and equivocations
  become evidence under the kernel's one law (per-machine Proposal/Vote
  registries) and revoke their author; heartbeat signing (ML-DSA) plus
  the crediting rule (credited iff every owed vote was cast).
  **The finish-line simnet passes**: 10 machines, 3 Byzantine (two
  double-propose, one equivocates), 24 rounds, votes delivered 2 rounds
  late — all 24 rounds finalize exactly one block, every Byzantine act
  yields evidence + revocation, honest machines are heartbeat-credited
  in all 3 epochs, and two instances with different insertion orders
  agree on the linearization and the finalized set.
- `crates/poe-net` (1/1 test) — **libp2p gossipsub** as the flow names:
  topics `poe/blocks`, `poe/votes`, `poe/acts`, content-hash message
  ids (dedup), mDNS + direct dial. Two nodes on localhost exchange
  block and vote payloads in the integration test. (The unadopted
  transport proposal document is a different design and is not what
  this crate implements — noted in the crate docs.)

Simnet runtime note: the finality battery takes ~3 minutes in a debug
build on this VM (XMSS/ML-DSA in debug profile), all of it crypto, none
of it waiting.
