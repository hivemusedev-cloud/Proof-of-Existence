# poe-node

The Proof of Existence blockchain node, built in Rust against the verified
Lean specification (`Proof_of_Existence_v1_1_1_CC.lean`).

**Public testnet `poe-testnet-1` is live** (Step 12c, launched 2026-11-13):
see [`testnet/TESTNET.md`](testnet/TESTNET.md) for how to join and
[`testnet/BOUNTIES.md`](testnet/BOUNTIES.md) for the three falsifier
bounties (F-Height, F-Clone, F-First-Year).

## Increment 1 — poe-kernel (this build)

A definition-for-definition port of the Lean kernel's core:

- `crates/poe-kernel/src/lib.rs` — claims (`Spend`), settlement (`settle`,
  `register`, `first_tx`, `evidence`), multi-height settlement (`settleM`),
  the money constants and grant law (`pot`, `grant`, `emission`), and a
  stateful `Registry` over the kernel's ten registry kinds.
- `crates/poe-kernel/src/ledger.rs` — notes, assets, the five acts
  (`Op::Join / Create / Issue / Transfer / Tick`), validity predicates, and
  the genesis ledger, mirroring the Lean `Ledger`/`act`/`runOps`.
- `crates/poe-kernel/tests/kernel_batteries.rs` — acceptance batteries
  modelled on the Fortran twin's T1/T2 streams and on the Lean theorems
  (`settle_nodup`, `settle_canonical`, `merge_registers_the_union`,
  `evidence_is_complete`, cap and window rules).
- `crates/poe-node` — a small demo binary: genesis → join → close → spend →
  double-spend refused.

Deliberate porting choices: std-only (no dependencies in the kernel); Lean
`Nat` becomes `u64` (heights/ids) and `u128` (value sums); Lean's division
by zero = 0 is preserved in `pot_share`.

## Increment 2 — the renewal act (Step 0, done 2026-11-13)

Approved design: `~/workspace/poe-build-2026-11-11/RENEWAL_ACT_DESIGN_DRAFT_2026-11-11.md`.
The Lean kernel was extended first (`~/workspace/poe-build-2026-11-11/lean-extension/`):

Liquidity, Tokenomics) recompile on Lean 4.19.0 with zero output, pins silent;
the Tokenomics envelope theorems now cover histories containing renewals,
machine-checking §16.4's "renewal raises no bound". The original verified
copies in `~/workspace/poe-verify-2026-11-10/` are untouched.

Rust port: `Op::Renew` + `valid_renew` + `Ledger.claimants` in poe-kernel;
Tick needed no change — renewal notes ride the same `regs` list and are born
at the close at the epoch's grant. Acceptance battery R1–R6 in

at caps MAX/7/0, double claim refused, grant spends exactly once, empty-pot

## Increment 3 — crypto carriers (Step 2, done 2026-11-13)

`crates/poe-crypto` (10/10 tests):

- `hash` — `H`, byte-for-byte the Compute Seed's construction: SHAKE256
  under `b"PoE/" + tag`, length-framed parts, naturals in 64-byte
  big-endian, 512-bit output. Test vectors generated by the Python original
  match exactly. Merkle commitments ported with the seed's odd-node-carried-up
  rule and empty-root constant.
- `tickets` — hash-chain proposal tickets: commit the tip, reveal one link
  per round, hashing forward verifies; win below `16/A` of the range.
  Boundary test is exact (the reference ticket wins at A=25, loses at 26);
  a 4,000-reveal census at A=200 lands near the expected ~320 winners.
- `xmss` — one-time vote keys: WOTS+ leaves (w=16) under a Merkle tree.
  The state discipline is the deliverable: an index is reserved and the
  state file persisted (write + fsync + atomic rename) *before* any
  signature is produced, so a crash burns a leaf but can never reuse one —
  covered by a crash-simulation test. Single-tree member of the family;
  the manual's 2^40-leaf multi-tree layering + production audit are Step 5
  hardening, stated in the module docs.
- `pq` — ML-DSA-87 (signatures, 4,627-byte sigs) and ML-KEM-1024 (messaging
  key establishment) as thin wrappers over the audited `fips204`/`fips203`
  crates; no cryptography implemented in-house. SLH-DSA not wired — ML-DSA
  covers the signature carrier; SLH-DSA stays a named alternative.

## Increment 4 — storage (Step 3, done 2026-11-13)

`crates/poe-store` (5/5 tests), plus kernel additions `Ledger::pruned`
(the Lean `pruneL`, ported), `Ledger::accepts` / `is_input_ok`, and
`Registry::restore`:

- Canonical encoding (fixed-width big-endian) for notes, acts, ledgers,
  spends — identical bytes on every machine.
- Append-only act log (length-framed, checksum per record) + atomic
  snapshots; replay on open rebuilds the ledger, and a torn tail from a
  crash mid-write is detected and dropped, never applied (tested).
- Per-epoch **state roots**: at each close, `H("state-root", …)` chaining
  the previous root, epoch, minted, live coin, a running births
  accumulator, and set sizes. Pruning never touches the root chain, so
  pruned and full nodes with the same history hold the same roots.
- Pruning verdict battery (T16 mirror at battery scale): a history run
  530 epochs — past the 522 window — then 10 candidate acts (replayed
  join, fresh join, renewals, creates, issues at/over the kept remainder,
  burned and dead inputs) whose verdicts agree between full and pruned,
  plus the input-verdict statement of `the_window_is_enough` itself.
  Scoping, stated in the test: candidates use genuinely fresh marks, as
  honest acts do; reusing a *forgotten* mark is the one case pruning
  cannot see, by design.
- Cuckoo filter over window nullifiers: no false negatives (10,000/10,000
  found), false positives under the 1% bound — an index only; verdicts
  always confirm against the exact death set.
- Backend note: the store is the workspace's own log+snapshot format
  behind the `Store` API. The API is the contract; a RocksDB backend can
  replace the files behind it later without touching callers (its C++
  build is deliberately not pulled into this workspace yet).

## Increment 5 — ordering + finality + networking (Step 4, done 2026-11-13)

Built exactly as BUILD_FLOW Step 4 specifies — three new crates:

- `crates/poe-dag` (3/3 tests) — BlockDAG assembly and **GHOSTDAG
  linearization implemented from the PHANTOM/GHOSTDAG spec**: selected
  parent by blue score, mergeset considered in decreasing blue-score
  order, a candidate is blue iff at most `k` current blues sit in its
  anticone. Content-addressed blocks (`H("block", …)`), so the total
  order is a pure function of the block set — the battery proves two
  DAGs fed the same 60 blocks in different valid orders produce the
  identical linearization and identical blue scores. This replaces the
  manual's imported ordering assumption with tested code.
- `crates/poe-finality` (2/2 tests) — round beacons (`H` over a
  finalized reference block, domain-separated — see the live-network
  corrections under Step 12c below); proposal draws verified against the
  committed ticket chain under the manual's 16/A rule; committees
  sampled by tickets (target 32); XMSS one-time votes with leaf-reuse
  rejection; **>2/3 finality**; double-proposals and equivocations
  become evidence under the kernel's one law (per-machine Proposal/Vote
  registries) and revoke their author; heartbeat signing (ML-DSA) plus
  the crediting rule (credited iff every owed vote was cast).
  **The finish-line simnet passes**: 10 machines, 3 Byzantine (two
  double-propose, one equivocates), 24 rounds, votes delivered 2 rounds
  late — all 24 rounds finalize exactly one block, every Byzantine act
  yields evidence + revocation, honest machines are heartbeat-credited
  in all 3 epochs, and two instances with different insertion orders
  agree on the linearization and the finalized set.
- `crates/poe-net` (1/1 test) — **libp2p gossipsub** as the flow names:
  topics `poe/blocks`, `poe/votes`, `poe/acts`, content-hash message
  ids (dedup), mDNS + direct dial. Two nodes on localhost exchange
  block and vote payloads in the integration test. (The unadopted
  transport proposal document is a different design and is not what
  this crate implements — noted in the crate docs.)

Simnet runtime note: the finality battery takes ~3 minutes in a debug
build on this VM (XMSS/ML-DSA in debug profile), all of it crypto, none
of it waiting.

## Step 12 — genesis, devnet, and the public testnet (12c, live)

- `poe-node` genesis builder: profile + launch + attestation roots →
  a genesis bundle whose hash commits to every constant; moving any
  constant is a different chain (tested). The single-node devnet
  (`poe-node devnet [dir]`) runs joins, a close, a transfer, snapshot
  and restart-replay against the real store.
- The testnet node (`poe-node testnet`) holds a persistent identity,
  self-attests under the chain's published test root (testnet-only:
  identities are free by design; mainnet roots belong to
  manufacturers and are never published), and runs the round loop —
  reveal, propose, vote, finalize, apply, epoch close — over libp2p
  gossip. Late joiners sync from a per-epoch bundle (`--sync-from`)
  written by every node at each close.
- Chain: `poe-testnet-1`, genesis hash
  `6107532c003ef90c66a1fb1151436803600a7e3600c312b96e6639b4304ab35f9c6776a8dc9994cff8064a5122022a8edc7966956860cfbbd50e4360d4e3de8e`,
  16 rounds per epoch, 3-second rounds, GHOSTDAG k = 3. The
  genesis hash does not depend on the clock; the current t0 and
  bootstrap identities live in `testnet/TESTNET.md`. Spec:
  `crates/poe-node/testnet-1.spec` (copy in `testnet/`).

### Live-network corrections (found by running it, 2026-11-13)

The lockstep simnet passed from the start; the live network did not
converge until four network-facing readings were corrected. The
kernel and money rules are untouched; each correction is also
documented at its code site.

1. **Beacon anchor.** Round beacons hashed the node's *current
   selected tip*, which changes with every block a node happens to
   have received — two honest nodes sampled different committees and
   refused each other's proposals. Beacons now hash the *finalized
   block of the round two back* (the genesis block for rounds 0–1): a
   fixed point every honest node holds identically.
2. **Reveals are buffered, not dropped.** A ticket reveal that
   arrived before its machine's registration had landed was refused
   and lost; that node's committee for the round silently shrank
   (in the worst case to itself, finalizing its own block). Reveals
   are now held until registration lands, and gossip messages carry a
   nonce so republication is not suppressed by content-hash dedup.
3. **Rounds are never skipped.** The round loop took its round from
   the wall clock; a node whose pre-genesis wait overshot genesis by
   one round never closed round 0's committee and never cast its
   vote, stalling the chain one vote short of finality forever.
   Rounds are now processed strictly in sequence; a node behind the
   clock replays its missed rounds back-to-back.
4. **Heartbeats sign after finality.** The epoch heartbeat commits
   to the finalized tip of the epoch's last round, but was signed at
   the boundary round — one round before that tip was final — over
   the zero tip no verifier accepts. Heartbeats are now signed in
   the first round where the epoch's last round is final, and closes
   wait one further round so peer heartbeats can arrive.
5. **Bundle joiners catch up over gossip; restarts resume.** The
   first live late joiner stalled permanently: its bundle ended at
   an epoch boundary, the votes for the rounds since had been cast
   before it came online, and gossip has no memory. Nodes now retain
   accepted votes and reveals for a bounded window and re-serve the
   current epoch's history when a new machine registers, so a joiner
   finalizes the gap in-protocol. And a restarted node restores from
   the bundle in its own data directory, rejoining at the frontier
   with its pre-restart rounds marked missed — re-claiming a round
   it already proposed or voted in could be evidence against itself.
6. **Windows fsync needs a writable handle** (found on a Windows
   run, 2026-11-13). XMSS persistence re-opened its temp file
   read-only to fsync it; Windows refuses to flush a read-only
   handle (`PermissionDenied`), so no vote key ever persisted
   there. The same pattern in the store's snapshot and registry
   writes is fixed the same way.

### Live-network corrections, second night (2026-11-14)

Running the third genesis for hours, under restarts and churn,
found the next layer — all in the network-facing node, none in the
kernel or money rules:

7. **Full finality snapshots.** Bundle-only resume rewound a
   restarted node to the last epoch close and re-marked everything
   since as missed; worse, a node killed mid-epoch resumed into a
   stall (its votes for the current epoch existed only in memory).
   Nodes now persist their complete finality state after every
   round (`finstate.bin`: committees, reveals, vote store, claims
   above a floor at the last finalized epoch) and resume from their
   exact position, re-casting their own votes for unfinalized
   rounds — the registry makes peers treat them as duplicates,
   never as second claims.
8. **Catch-up dwells.** A bundle joiner raced through its gap
   rounds in milliseconds and closed their committees before peer
   history arrived — finalizing a solo view an epoch long. A
   catching-up node now waits, briefly and boundedly, for peer
   reveals and blocks for a past round before closing its committee
   or voting in it.
9. **History retention 2 → 16 epochs**, and announcements now carry
   the announcer's live position (`sync_hint`), so a joiner asks
   for — and the network re-serves — the rounds that actually lead
   to the frontier.
10. **Canonical-proposal guard.** A sequentially resumed node
    re-processed rounds it had proposed in before the kill and
    minted *second, different* blocks for them — manufacturing
    equivocation evidence against itself and its peers. A node
    that already holds a canonical proposal for a round re-serves
    it and never mints another.
11. **Orphaned-join retry.** The join marker cleared only when the
    join landed in the ledger; a join proposed in a block that
    never finalized was therefore never proposed again — a late
    joiner could wait forever, silently. Once the proposing round
    is final without the join, the marker clears and a later round
    re-proposes. (Proven live: epoch 76, `claimants=1`.)
12. **Mesh hygiene under load.** Three scale bugs in one: votes
    re-served by history were fully re-verified (XMSS) even when
    already recorded — a duplicate fast path now answers first,
    and vote() closes a round's committee on demand when its
    beacon anchor is already final; the periodic peer re-dial
    opened a *new* connection every time (160 connections among 4
    nodes, starving the hub) — dialing now skips connected peers;
    and history was re-served as the whole retained range every
    round — it is now walked in slices.

**The open finding — liveness under churn.** Even with all of the
above, a round whose drawn committee loses a vote (a voter
crashes, lags an epoch, or votes a different block after late
delivery) can sit one vote short of finality forever: committees
are drawn once, votes are one-time claims, and finality is
sequential. The chain stalled this way at rounds 752, 1084 and
1231. Recovery today is an operator re-anchor from the last epoch
bundle — final state is never lost, the unfinalized tail is
discarded. Whether the protocol itself gains a liveness mechanism
is a design decision for its authors, not a patch; the full
account is in `testnet/TESTNET.md` (operations log).

Acceptance evidence: genesis of 2026-11-13 21:14 +06 — three nodes
over real libp2p finalized in lockstep with identical closes
(epoch 0: 3 claimants × 100,000, credited 3, root
`101456563fc6902d`). Current chain (third genesis, 2026-11-14
00:30 +06): epochs 0–66 identical on three nodes; a mid-epoch
restart resumed from finstate and kept closing identically; at
epoch 76 a late joiner's join landed on independent nodes with
root `d68cda776b23a5c9` (`claimants=1, grant_each=99999`). Full
workspace suite after all corrections: **67/67 tests pass**
(2026-11-14). A note on zero-claimant epochs: that is the kernel's
own law, not a stall — `Join` is once-ever per machine and later
claims come from new joins and from renewals after 25 faithful
epochs.

The first genesis (20:52 +06) ran for nine minutes before the
late-joiner gap in correction 5 was found; the chain was reset
before any external participation. Two further geneses and four
clock re-anchors followed on 2026-11-14, all before external
participation — and none could have had any: the operator's VM
has no inbound reachability (see `testnet/TESTNET.md`). The
chain's current position and bootstrap identities are kept
current in `testnet/TESTNET.md`, not here.
